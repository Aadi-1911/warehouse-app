# Learning Log

Three things live here: **Decisions & Reasoning** (why we built things the way we did, what we didn't do instead, and why), **Mistakes & Fixes** (real problems hit during the build, how they were diagnosed, and why the actual fix is correct — not just a workaround), and a **Concepts** glossary. This file grows continuously as the actual build happens — the moment a real decision gets made, something breaks, or a new concept comes up, even mid-task. Covers backend and frontend equally. Concept entries aim to be complete enough to actually understand the idea, including whatever context it depends on, not just a one-line definition. See CLAUDE.md for the full instruction. This file is the "why" (and "what went wrong") behind everything; the other numbered `.md` docs in this folder are the "what."

## Decisions & Reasoning

### Why this business, this way (the founding idea)
The project serves two goals at once: a real tool for a real wholesale garment business, and a genuine full-stack learning project. When they conflict, the business wins — this was stated explicitly early on ("if it's boring, it should be a win for the business, not the resume"). This single rule ended up settling almost every later scope argument without needing a fresh debate each time.

### Why Phase 1 is Inventory only, not the full system
The full picture that emerged through design (Inventory + Parties + Orders + Billing + Payments) is, honestly, a lightweight ERP — a much bigger build than "an inventory app." Rather than building all of it before shipping anything, we cut to the single piece that mattered most *right now*, confirmed directly rather than assumed. Building everything at once would have meant months of planning with nothing real in daily use, and no early feedback to catch mistakes cheaply. Shipping Inventory alone, in real use, teaches more per hour than a bigger unfinished build ever would.

### Why React is kept separate from the backend (not Next.js)
Next.js would merge frontend and backend into one project — less boilerplate, but it hides the actual HTTP request/response boundary between client and server. Keeping them as two separate projects forces genuine understanding of what a REST API is, why CORS exists, and how a real client talks to a real server — foundational, transferable knowledge that a merged framework lets you skip entirely. The cost (a bit more deployment complexity, two services instead of one) is small next to what's gained.

### Why Prisma over raw SQL
Raw SQL (writing every query and migration by hand) teaches the most, but costs the most time for a total beginner — a real risk against a job-hunting timeline. Prisma turned out to be the rare case where the *easier* option isn't actually a shortcut: the schema file is basically a formalized version of the entity model already designed by hand, migrations are generated and inspectable, and Prisma Studio gives a real GUI into the data. The habit that keeps it honest: periodically turn on query logging and read the SQL it generates, so it never becomes a total black box.

### Why auth is hand-rolled, not a managed service (Clerk/Auth0/etc.)
At 2–5 users, a managed auth service doesn't save much real time — and the app has a genuinely non-standard requirement (role check *plus* a separate PIN specifically for price edits) that doesn't fit a generic login SDK's assumptions anyway. Rolling it means real, interview-relevant understanding of password hashing, sessions, and protected routes, for roughly the same effort as fighting a tool that wasn't built for this shape of requirement.

### Why a website (PWA), not a native app
Native apps earn their complexity when they unlock something a browser genuinely can't do well — offline-first sync, camera/barcode scanning, heavy push notifications. None of those are actually needed here: connectivity in the field is mostly reliable (occasional drops fall back to manual re-entry), and there's no barcode-scanning workflow in how articles get selected. A skilled team with unlimited resources would build the same thing — a responsive PWA — because nothing about the actual business creates an advantage for native at this scale.

### Why Bundle = Product + Color, and sizes are fixed per Product
Early assumption was that sizes might need tracking per bundle or per color. Stress-testing against how the business actually operates revealed the size range is always the same for a given article — a different size range simply gets a different Article No. entirely. This *simplified* the model rather than complicating it: sizes belong once, at the Product level, not duplicated everywhere a color or bundle appears.

### Why Stock is a join table (Bundle × Location), not a single number per Bundle
A single stock count per Bundle couldn't represent the real situation: the same Bundle (e.g. Article A101 in Navy) can have different quantities sitting in Delhi versus Gurgaon. Splitting Stock out as its own table, keyed on both Bundle and Location, was the only way to represent that truthfully.

### Why cost_price/sellingPrice are nullable ("pending price"), not required at creation
Forcing a price to be set the moment an article is created would block staff from logging a receiving session for a genuinely new article until the owner was available — unrealistic given staff and owner are never even on the same device (phone vs. PC). Making price nullable let receiving and pricing become two independent steps: staff can log what physically arrived immediately, and a "pending price" badge naturally signals what still needs the owner's attention, without inventing a separate approval workflow.

### Why price editing needs a PIN, not just the owner role
This one got revised. The first answer was "owner-role login is enough" — but that quietly dropped an explicit original requirement (owner wanted protection "even for himself," given how sensitive cost data is). Revisiting it: role alone proves *who's logged in*, not that *this specific action* was intentional. The PIN is a second, action-specific confirmation — small cost, but it restores a requirement that almost got lost in simplification.

### Why Order status is four stages, not three
A prototyping tool's demo collapsed this to Open → Packed → Shipped, skipping "Billed" entirely. But billing is a genuinely separate, harder problem (a real invoice document, GST fields, e-way compliance) that hasn't even been designed yet — collapsing it into "shipped" would hide that dependency and make it easy to accidentally ship something that was never properly billed. Keeping Billed as its own stage keeps that gap visible instead of papered over.

### Why "adjusted" is a logged event, not a status value
Orders can change at any point — before packing, during packing, even after, per how the business actually operates. Modeling that as a status (`Placed → Adjusted → Packed`) would require illegal-looking backward transitions once packing had already started. Instead, status stays simple and linear (Placed → Packed → Billed → Shipped), and every change is a separate append-only log entry layered on top — the full history is visible without corrupting the simple state machine.

### Why payments default to FIFO but allow a mandatory-reasoned override
Most payments are simple — pay the oldest bill first. But real Parties don't always pay against the bill you'd expect. Forcing pure FIFO would misrepresent reality; allowing free-form override with no record would make it untraceable. Requiring a note *specifically when* someone overrides the default keeps the common case frictionless while keeping every exception explainable later.

### Why the "outstanding amount" tracker is separate from the real Bill
Full invoice generation (matching the business's actual Excel template, GST fields, e-way thresholds, immutability, corrections) is a genuinely bigger, harder, still-undesigned problem. But the owner needs *some* visibility into who owes what well before that's built. Splitting them meant shipping real value now without waiting on — or accidentally under-designing — the harder piece.

### Why Kids sizing reuses the adult sizing rule instead of a new 4pc/6pc lookup table
The obvious approach would hardcode "kids sets are 4 or 6 pieces." But the adult rule (pieces-per-set = however many size options got selected) already generalizes perfectly to age brackets — 4 brackets selected = a 4pc set, 6 selected = a 6pc set. Recognizing the existing rule already covered the new case avoided inventing and maintaining a second, redundant system.

### Why low-stock is a small badge, never a fully-tinted card
An early version tinted the whole card/row for any shortfall. In practice, that trains people to tune out red over time (alarm fatigue) — and makes genuinely urgent situations blend in with routine ones. A small flag, reserved for a specific threshold (≤2 sets), stays meaningful precisely because it's rare.

### Why session items snapshot their Factory/Location/price instead of reading it live
If a receiving session's item just referenced the session-level Factory/Location dropdown, changing that dropdown mid-session (e.g. realizing halfway through that goods are actually going to a different warehouse) would silently corrupt every item already entered. Capturing those values on each item *at the moment it's finalized* means later changes can't reach backward and corrupt earlier data — a real bug class avoided by design rather than caught by testing.

### Why jsonwebtoken/express-session weren't installed yet
`02_ARCHITECTURE.md` §4.1 explicitly leaves session-vs-JWT as an open choice ("either is acceptable, pick one"). That's a real auth-design decision, and building auth is its own future task — so the backend-init task (npm init + minimal server) only installed what's needed for *any* server to exist (express, cors, dotenv, bcrypt, prisma), not the auth-token library itself. Avoids default-picking an approach that should get a deliberate answer when we actually build login.

### Why cors and dotenv were added even though the doc only names Express/Prisma/bcrypt
Neither is a business-logic choice — they're plumbing required by decisions already made elsewhere in the doc: `cors` exists because frontend and backend are separate deployments (§3), so the browser needs an explicit "this origin is allowed" signal or every request gets blocked. `dotenv` exists because the doc's own env var list (§7) has to be loaded into the app somehow. Neither adds a new capability beyond what was already decided; they just implement it.

### Why the schema was transcribed from 03_DATABASE_SCHEMA.md §1 rather than redesigned
That document already *is* the finalized Phase 1 data model — the entity design work happened when it was written, not now. Copying it verbatim (including its own inline comments) avoided silently second-guessing decisions already made, and kept that task scoped to "get the schema into the database," not "redesign the schema."

### Why the schema alone doesn't enforce cost_price visibility, the PIN gate, or atomic stock writes
Prisma's schema language can describe *shape* (a `Decimal?` field can hold null or a number) but not *behavior* (who's allowed to read a field, or that a write must happen alongside an audit row). Those four rules — no `cost_price` to STAFF, PIN + OWNER role to edit prices, Stock only changes via a `Transaction` insert, Bundle/Color pairs validated before accepting a transaction — all have to be checked in the Express controllers/middleware that sit in front of Prisma, not in the schema file itself. The schema just makes the *right* shape possible (e.g. `Stock.qtySets` has no API to edit it directly yet — there's no route for that at all).

### Why the database was checked for existing tables before migrating
`prisma migrate dev` can be destructive if it detects drift against an already-populated database (it may prompt to reset). Since the Neon database was freshly provisioned, checked first with `prisma migrate diff --script` (prints the SQL Prisma would run without applying it) — confirming it was 100% `CREATE TABLE`/`CREATE TYPE` with no `ALTER`/`DROP` statements, meaning the database was genuinely empty and there was nothing at risk of being overwritten.

### Why History edits create a new entry instead of overwriting in place
The founding principle for the whole system is that every number traces back to a logged event — nothing is ever just manually edited with no trace. A literal in-place edit (even with an "(edited)" tag) still destroys the original value. A new correcting entry costs a little more complexity but keeps that principle intact even when accommodating real mistakes.

### Why JWT was chosen over session-based auth (02_ARCHITECTURE.md §4.1)
The deciding factor was the deployment topology, not a general preference: frontend (Vercel) and backend (Railway/Render) are separately deployed, almost certainly different origins in production. Session auth needs a cookie sent back on every request, and a cookie shared across two different origins needs `SameSite=None; Secure` plus matching CORS `credentials: true` on both sides — a genuinely fiddly cross-site configuration, especially on mobile Safari/PWA (the staff device profile). It would also need a server-side session store so sessions survive a server restart. JWT sidesteps both: the client carries its own signed token via an `Authorization: Bearer` header, no cookies or session store needed at all — and it reinforces the same "explicit client-server boundary" lesson that's the whole reason frontend/backend are kept separate in the first place (§3).

### Why the auth middleware re-fetches the user's role instead of trusting the JWT payload
Textbook JWT usage trusts whatever role is embedded in the token, since that's the whole "stateless" point of JWTs. But `cost_price` visibility is the one rule CLAUDE.md calls non-negotiable "under any circumstance" — a still-valid old token must not keep granting a role the user no longer has (e.g. if an account got demoted or disabled after the token was issued). So the token only carries `userId`; the middleware looks up that user's *current* role from the database on every request. This costs one extra DB read per request, which is free at 2–5 users, in exchange for the role check always reflecting reality.

### Why the price-edit PIN is a 6-digit bcrypt hash, not a 4-digit or plaintext one
Reused `bcrypt` (already in the codebase for the login password) rather than adding a second hashing library for a second secret on the same `User` model — no real reason to diverge. Length was an open choice the docs didn't specify: went with 6 digits (1,000,000 combinations) over the more common 4-digit ATM-style PIN (10,000), because unlike a bank PIN this one isn't backed by a physical card that gets seized after a few wrong tries — the only real defense here is entropy plus rate limiting together, so it was worth the small extra typing cost.

### Why PIN rate limiting is per-user and DB-backed, not IP-based or in-memory
IP-based limiting is the wrong shape for this threat model — it wouldn't stop an attacker using a stolen JWT from the owner's own network, and with a single OWNER account there's no meaningful "per-IP" pattern to distinguish attacker from owner. Tracking `failedPinAttempts`/`pinLockedUntil` directly on the `User` row instead means the lockout is tied to the specific account being attacked, and survives a server restart or a future move to multiple backend instances — an in-memory counter would silently reset on either.

### Why the seed script backfills the dev PIN only if missing, instead of always setting it
The OWNER row already existed from the previous task's seed run, before this PIN feature existed — a plain re-seed wouldn't touch it, since `passwordHash` and now `priceEditPinHash` are only ever set once (at creation, or via this one-time backfill), never overwritten by re-running the script. This matters beyond just fixing today's already-existing row: once a real "change PIN" endpoint exists, re-running `prisma db seed` (e.g. during a fresh environment setup) must never silently revert the owner's real PIN back to the `123456` dev default.

### Why costPrice omission uses Prisma's `select`, not fetch-everything-then-delete-a-key
Both approaches can produce identical JSON for a STAFF response today. The difference shows up under future change: if some later route did `res.json({ ...product, extra })`, a fetch-everything approach would silently leak `costPrice` back in the moment anyone forgot to re-delete it, while a `select`-based approach means `costPrice` was never fetched from Postgres in the first place for a STAFF request — there is no key to accidentally reintroduce, because it was never in the JS object at all. Given CLAUDE.md's "under any circumstance" wording for this specific rule, the version that's structurally incapable of the leak (not just currently-correct) was worth the small extra `productSelect(role)` indirection.

### Why the API's error responses were retrofitted to `{ error: { code, message } }` mid-task
`auth.js`, `authController.js`, `requireRole.js`, and `requirePin.js` were all built in earlier tasks using a flatter `{ error: "string" }` shape and somewhat improvised status codes (e.g. 400 for a missing PIN, 423 for a lockout) — reasonable guesses at the time, but built before `04_API_SPEC.md`'s "General Error Conventions" section had been read closely. That section is explicit that *all* error responses share one shape, and specifically classifies "missing/invalid PIN" under `403`, not 400/401/423. Since this task's whole point was wiring `requireRole`/`requirePin` into a real spec-driven endpoint, shipping new endpoints that were spec-correct on top of old middleware that wasn't would have produced an inconsistent API on day one — cheaper to fix the four existing files now than to leave two different error shapes coexisting.

### Why POST duplicate-article and missing-factory checks catch Prisma errors instead of pre-checking existence
A "check if it exists, then insert" pattern has a race window — two near-simultaneous requests could both pass the check before either insert lands, and the database's own unique constraint would still catch it, just after doing unnecessary work. Instead, `createProduct` attempts the insert directly and catches Prisma's `P2002` (unique constraint violated → 409 duplicate article) and `P2003` (foreign key violated → 404 factory not found) — the database's constraints are already the actual source of truth for these rules (`@@unique([articleNo, factoryId])`, the `factoryId` foreign key), so there's no separate check to keep in sync with them or race against.

### Why PATCH rejects articleNo/factoryId instead of silently allowing or ignoring them
`04_API_SPEC.md` doesn't enumerate exactly which fields are PATCH-able ("any subset of editable fields... category, etc."). Silently ignoring an attempt to change `factoryId` would be confusing — a client sending `{ factoryId: 'x' }` and getting a 200 with no visible effect looks like a bug, not a deliberate rule. Explicitly rejecting with 400 makes the constraint visible: changing either field after creation could violate the per-factory article-uniqueness rule or orphan Bundles/Stock rows still tied to the original factory, so it's excluded on purpose, not by omission.

### Why POST /api/locations was built as OWNER-only, even though the task described it as "any authenticated role"
`04_API_SPEC.md` explicitly marks `POST /api/factories` and `POST /api/colors` as 🔒 (any role) but `POST /api/locations` as 👑 (OWNER only) — a real, specific difference from the other two, not a typo skimmed past. Since the doc is the named source of truth for this task ("build...from 04_API_SPEC.md"), built it as the doc states and flagged the discrepancy rather than silently following the paraphrase or silently following the doc without saying anything — either silent choice would have left a real mismatch undiscovered.

### Why Color/Location uniqueness uses a case-insensitive app-level check plus a P2002 catch, not a case-insensitive database index
The schema's `name @unique` on both models is a plain Postgres unique index, which is case-sensitive by default — "Navy" and "navy" wouldn't collide at the DB level alone. A fully database-enforced case-insensitive constraint is possible (a functional index on `LOWER(name)`, or the `citext` extension) but needs hand-written SQL in the migration, extra complexity for what `04_API_SPEC.md` itself only calls "recommended" on a low-traffic lookup table with 2–5 users. A `findFirst` with `mode: 'insensitive'` before the insert, plus catching `P2002` as a backup for the exact-case race, is proportionate to the actual stakes here — unlike `costPrice` visibility, a duplicate color slipping through under rare concurrent-request timing is a minor cleanup annoyance, not a rule CLAUDE.md calls non-negotiable.

### Why Location got the same case-insensitive treatment as Color, though the spec only says it for Color
`04_API_SPEC.md`'s case-insensitivity language ("recommended, to avoid 'Navy' vs 'navy' duplicates") appears only in the Colors section, not Locations. But Location names are the same shape of problem — a short free-text field ("Delhi" vs "delhi") — so applying the same pattern for consistency seemed like the more helpful default. Flagging this explicitly since it's an extension by analogy, not something the spec literally states for Locations.

### Why Bundle creation pre-checks Product/Color existence instead of only catching a Prisma FK error
Products' `createProduct` catches `P2003` for its one foreign key (`factoryId`) and that's unambiguous — there's only one thing it could be. Bundles have *two* foreign keys (`productId`, `colorId`), and a bare `P2003` doesn't cleanly identify which one failed without fragile parsing of Prisma's error internals. Two explicit `findUnique` existence checks before the create cost two extra queries but give an unambiguous `PRODUCT_NOT_FOUND` vs `COLOR_NOT_FOUND` — worth it here specifically because of the two-FK shape, not a blanket departure from the catch-the-constraint pattern used everywhere else (the actual uniqueness rule, `(productId, colorId)`, still gets caught via `P2002`, same as Colors/Locations/Products).

### Why POST /api/transactions guards the negative-quantity check inside the UPDATE's WHERE clause, not with a separate read-then-check
This is the endpoint every Stock number in the app flows through, so it got more care than a typical CRUD write. The naive version — read `qtySets`, check in JS whether subtracting would go negative, then write the computed value — has a real race: two near-simultaneous requests against the same Stock row could both read the same starting value, both pass the check, and both write, letting stock go negative despite the check technically existing. Instead, `buildStockUpdate` produces a Prisma `updateMany` with the guard baked into the `where` clause itself (e.g. `where: { id, qtySets: { gte: qtySets } }` combined with `data: { qtySets: { decrement: qtySets } }`) — this compiles to one atomic SQL `UPDATE ... WHERE qtySets >= ?`, so the database evaluates the guard against the true current value at the exact moment it applies the write. A `count: 0` result means the guard failed, which is how the negative case gets detected — there's no window where two requests can both pass a stale check.

### Why the whole find-or-create-then-update-then-insert sequence runs inside one `$transaction` callback, not the array form
Prisma's array form (`$transaction([op1, op2])`) only works for a fixed, pre-determined list of operations — it can't express "read something, then conditionally decide to error out based on that read." The callback form (`$transaction(async (tx) => {...})`) runs everything on one real Postgres transaction, and throwing inside it rolls back *everything* the callback did so far — including the Stock row that the find-or-create step might have just created moments earlier for a bundle/location with no prior history. That specific case mattered concretely: attempting `STOCK_OUT` against a never-before-touched bundle/location creates a zero-value Stock row via `upsert`, then immediately fails the negative guard — without the rollback, that phantom zero-value row would persist even though the actual transaction was rejected. Verified this directly by counting `Transaction` rows after 3 deliberately-rejected attempts sandwiched between 4 real ones — exactly 4 exist, not 7, and Stock quantities matched exactly what the 4 successful operations should have produced.

### Why the catch-all error handler shows the real error message in dev but a generic one in production
Every other error in this API is deliberate — the code already knows exactly what's wrong (a duplicate name, a missing field) and `sendError()` names it specifically, matching `04_API_SPEC.md`'s "never generic 'something went wrong'" guidance. This handler is the opposite case by definition: it only fires when nothing upstream understood what happened, which means the raw `err.message` could contain anything, including internal details (stack traces, DB connection specifics, file paths) that shouldn't go out over the network to a client. Gating on `NODE_ENV` (already a tracked env var) gets both: real detail for local development, where seeing the actual message is genuinely useful, and a safe generic message once deployed, while the full error is `console.error`'d server-side either way so nothing is actually lost, just not exposed to the caller.

### Why GET /api/stock's response is a flattened, joined shape instead of the raw Stock row
`04_API_SPEC.md` specifies display-ready strings (`productArticleNo`, `colorName`, `locationName`) alongside `bundleId`/`locationId`, not the raw `Bundle`/`Product`/`Color`/`Location` records a Stock row actually relates to. This is a deliberate join, not a shortcut: the Live Stock View is meant to render a search/filter table directly from this response, and making the frontend separately fetch Products/Colors/Locations just to label each row would be real, avoidable extra work.

**Update:** the first version of this endpoint was built when the spec's response shape only listed `locationName`, not `locationId` — flagged at the time as a likely gap, since a client wanting to fire `POST /api/transactions` from a stock row needs the real `locationId`, not just its display name. `04_API_SPEC.md` was updated to add `locationId` to the documented response, and the endpoint (plus its test's field-set assertion) was updated to match. Worth remembering as a small case study in the doc-first workflow this project uses: flagging a suspected gap rather than silently patching around it meant the spec doc itself got corrected, not just this one endpoint's implementation quietly diverging from what's written.

### Why /api/users reuses the exact same "select, don't strip" pattern as costPrice
`GET /api/users` and `POST /api/users`'s responses never SELECT `passwordHash`/`priceEditPinHash` from the database at all, the same approach `productController.js` uses to keep `costPrice` away from STAFF — not "fetch the full row, then delete the sensitive keys before responding." Consistency mattered here specifically because these two fields are the actual credential material for every account in the system (a password hash and the price-edit PIN hash) — genuinely the highest-stakes fields in the whole schema to accidentally leak, more so than `costPrice`. Using the identical, already-proven pattern rather than inventing a new one for this endpoint keeps the guarantee structural in exactly the same way: there's no key to leak because it was never fetched, not because someone remembered to strip it.

### Why GET /api/products/:id/valid-colors lives in productController.js/routes/products.js, not its own file
The URL is `/api/products/:id/valid-colors` — a sub-resource of a specific Product, not an independent Bundle-listing endpoint (that's already `GET /api/bundles?productId=`, built earlier, which returns a different, un-joined shape). Since Express routes on path structure, not on which "resource" a route conceptually belongs to, mounting it as `router.get('/:id/valid-colors', ...)` alongside the other `/api/products/*` routes keeps the URL structure and the file structure in sync, rather than splitting one product's sub-paths across two different route files for no functional reason.

### Why GET /api/transactions' response shape includes locationName/locationId even though the spec's prose only says "bundle/product/color info"
Unlike most other endpoints, `04_API_SPEC.md` describes this response only in prose ("joined user name, bundle/product/color info for display"), not as a literal object — a real design decision, not a transcription. Included `locationName`/`locationId` anyway: the endpoint has a `?locationId=` filter, and filtering by something the response never displays would be a strange asymmetry — a history/audit view is close to meaningless without knowing *where* each entry happened. Otherwise reused the exact field names already established for `GET /api/stock` (`productArticleNo`, `colorName`, `locationName`) for the same underlying joined data, plus the raw IDs alongside each display string (`userId`+`userName`, `bundleId`+`productArticleNo`/`colorName`, `locationId`+`locationName`) — the same "IDs for linking, strings for display" shape `GET /api/stock` ended up with after its own `locationId` addition. Also defaulted to newest-first ordering (`createdAt: desc`), not stated in the spec but the standard expectation for an audit list — flagged all of this explicitly since none of it is spec-literal.

## Mistakes & Fixes

Every entry here follows the same five-part structure, backend or frontend, no exceptions: **(1) Original approach** — what was tried first and why it seemed right at the time. **(2) What went wrong** — the actual symptom, and how it was noticed. **(3) Diagnosis** — how the real cause was tracked down, not just guessed at. **(4) The fix** — what was actually changed. **(5) Why this fix is correct** — the reasoning for why it addresses the real cause, not just a workaround that happened to make the symptom disappear.

### Prisma CLI install failing outright on this machine
**(1)** Ran a plain `npm install -D prisma nodemon` in the backend, expecting npm to grab the latest stable release like any other package. **(2)** The install failed outright: `npm ERR!` from `prisma`'s own preinstall script, refusing to proceed. **(3)** The error message named the actual cause directly — Prisma 7.x requires Node `^20.19 || ^22.12 || >=24.0`, and this machine runs Node `20.12.2`, just short of the 20.19 floor. **(4)** Pinned both `prisma` and `@prisma/client` to `6.19.3` (confirmed via `npm view prisma@6 version`/`engines` to be the latest 6.x release, requiring only Node `>=18.18`) instead of the default-installed 7.9.1. **(5)** This is the correct fix, not a workaround, because it resolves the actual incompatibility (wrong engine requirement for this Node version) without touching Node itself — upgrading Node was out of scope for "initialize the backend," and both packages are still on a genuinely current, supported release line.

### Prisma Studio: "Response from the Engine was empty" on every query
**(1)** The reporting hypothesis was version drift between `prisma` and `@prisma/client` (reasonable, given the 7.x/6.19.3 pinning incident above), or a corrupted/wrong-architecture query engine binary. **(2)** Studio's browser UI threw "Response from the Engine was empty" the moment any model (confirmed on `Factory`) was queried. **(3)** Diagnosed layer by layer instead of guessing: `npx prisma -v` showed `prisma` and `@prisma/client` both at exactly `6.19.3` (no drift); the engine binary at `node_modules/.prisma/client/libquery_engine-darwin-arm64.dylib.node` was the correct size (~19MB, not truncated), a valid Mach-O arm64 binary matching this machine's actual architecture (`uname -m` → arm64), ad-hoc code-signed as expected for Prisma's Mac binaries, with no macOS quarantine flag blocking it, and all its dynamic library dependencies were plain system frameworks (Security, CoreFoundation, libSystem — nothing third-party to fail to resolve). A direct `@prisma/client` query (`prisma.factory.findMany()`) run from a small standalone script succeeded immediately, returning `[]`. To rule out something Studio-specific, traced Studio's own bundled server code (`node_modules/prisma/build/index.js`) to find its internal `/api` JSON-RPC endpoint, then replayed the exact `getDMMF` + `clientRequest` calls a real browser tab sends against a freshly started Studio instance — that succeeded too, returning the empty `Factory` table correctly. A process check also confirmed no stale Studio process was left running from whatever earlier session hit the error. **(4)** No code change was needed — every layer (dependency versions, the engine binary itself, the live database connection, and Studio's own request/response protocol) checked out working correctly against a fresh instance. **(5)** Since the identical schema, database, and engine binary succeed end-to-end when driven fresh, the original error couldn't have come from a persistent defect in this project's dependencies or files — the most consistent explanation is transient/stale state from the earlier session (e.g. a Studio tab left open from before the migration existed, whose cached schema hash no longer matched the database, or a since-closed Studio process in a bad state). If this recurs: fully close old Studio browser tabs/processes and relaunch fresh with `npx prisma studio --schema=src/prisma/schema.prisma`.

### Login endpoint returned 404 "Cannot POST /api/auth/login" despite the route being mounted correctly
**(1)** After adding `app.use('/api/auth', authRoutes)` to `server.js`, started the server in the background and curled `/api/auth/login` to test it end to end. **(2)** Got a 404 HTML error page ("Cannot POST /api/auth/login") — as if the route didn't exist at all, even though `server.js` clearly had it mounted. **(3)** `lsof -i :3001` showed a *different*, older node process already bound to port 3001, left running from an earlier session (probably the backend-init task's manual server test). Since that port was already taken, the freshly started server process silently failed to bind, and every curl request was actually hitting the stale old process — which predates the auth routes entirely. **(4)** Killed the stale process (`kill <pid>`), confirmed the port was free with `lsof`, then restarted the server. **(5)** This is the correct fix, not a workaround, because the code was never actually broken — the bug was in test hygiene (not verifying the port was free before starting a new instance), not in `server.js`. Re-ran the full test suite (login, `/me` with a valid/missing/garbage token, wrong password, unknown username) against the properly-started server and every case passed.

### Test cleanup failed on a foreign-key error when deleting a throwaway test Product
**(1)** After the full Products test suite passed, the test script's own cleanup step tried `prisma.product.deleteMany({ where: { factoryId: factory.id } })` to remove the throwaway test product before deleting the test Factory. **(2)** Postgres rejected it: `update or delete on table "Product" violates RESTRICT setting of foreign key constraint "ProductSize_productId_fkey"` — the delete never ran. **(3)** The cause was in the error message itself: each test `Product` had `ProductSize` rows (created via the nested `sizes: { create: [...] }` in `createProduct`) pointing back at it via a foreign key with the default `RESTRICT` behavior, which blocks deleting a parent row while children still reference it. **(4)** Deleted the `ProductSize` rows for each test product first, then the `Product` rows, then the `Factory`, then the test `User` — respecting the actual dependency order instead of deleting parent-first. **(5)** This is the correct fix, not a workaround: `RESTRICT` (Prisma's schema default when a relation doesn't specify `onDelete`) is doing exactly its job here, and it's the *right* job for this schema — silently cascading a `Product` delete into deleting its `ProductSize` rows would be a real footgun in the live app (accidentally deleting an article's size list by deleting the article), so the fix was to respect the ordering the constraint is enforcing, not to weaken the constraint.

## Concepts

**ORM (Object-Relational Mapper)** — Prisma, in our case. Instead of writing raw SQL by hand to talk to the database, you describe your data as JavaScript-like objects and the ORM translates that into SQL for you. You still end up understanding the database structure (the schema file basically *is* your data model), you just don't hand-write every query.

**Migration** — a recorded, versioned change to the database structure (e.g. "add a Product table"). Every time the schema changes, a new migration file gets created so the change can be applied to any copy of the database (your laptop, the live server) in the same order, and so there's a history of how the database evolved over time.

**Middleware** — code that runs *in between* a request arriving at the backend and it actually being handled. Used here for things like "check the user is logged in" or "check the user's role is OWNER" before the real endpoint logic even runs — a gatekeeper step.

**async / await** — most backend code has to wait on something slow (a database query, a network call) before it can continue. `async`/`await` is JavaScript's way of writing "pause here until this finishes" without freezing everything else the server is doing. You'll see it on almost every backend function that touches the database.

**REST API / endpoint** — a REST API is just an agreed set of URLs (endpoints) the frontend can call, each doing one specific thing (e.g. `POST /api/transactions` = "log a stock movement"). "Endpoint" just means one specific URL+action combination.

**Environment variable** — a setting (like the database connection string or a secret key) kept outside the actual code, usually in a `.env` file, so secrets never get committed to version control and the same code can run against different databases (your laptop vs. the live server) without editing code.

**JWT / session** — after you log in, the server needs a way to know it's still you on the next request without asking for your password every time. A session (a reference stored server-side) or a JWT (a signed token stored client-side) are two ways of doing that. We're using one of these — check the current code for which.

**package.json / npm install** — `package.json` is a project's manifest: its name, and every external library (package) it depends on. Running `npm install <package>` downloads that package (and anything *it* depends on) into a local `node_modules/` folder, and records the version in `package.json`'s `dependencies`. Anyone else who clones the project just runs `npm install` with no arguments and gets the exact same set of packages — the code itself doesn't need to be copied, just the manifest.

**dependencies vs. devDependencies** — both live in `package.json`, but mean different things. `dependencies` (installed with plain `npm install <pkg>`) are packages the app needs *at runtime* — e.g. `express`, since the live server actually calls into it. `devDependencies` (installed with `npm install -D <pkg>`) are tools only needed *while building/developing* — e.g. `nodemon`, which restarts the server on file changes but has nothing to do with how the deployed app behaves. Keeping them separate matters because some deployment steps install only `dependencies` to keep the production install smaller.

**CORS (Cross-Origin Resource Sharing)** — by default, a browser blocks JavaScript running on one origin (e.g. the Vite dev server at `localhost:5173`) from making requests to a different origin (e.g. the Express API at `localhost:3001`) — a security default, not a bug. The `cors` middleware on the backend explicitly tells the browser "requests from this specific origin are allowed," via the `Access-Control-Allow-Origin` response header. This only became necessary *because* frontend and backend are two separate projects/deployments (see the Next.js decision above) — a merged framework wouldn't hit this at all, since there'd be no cross-origin request to begin with.

**nodemon** — a dev-only tool that watches your backend source files and automatically restarts the Node process whenever one changes, so you don't have to manually stop/rerun `node src/server.js` after every edit. Only affects the local dev workflow — production runs plain `node src/server.js` (the `start` script), not nodemon.

**Migration (in practice, this project's first one)** — running `npx prisma migrate dev --name init_phase1_inventory` did two things: (1) generated a `migration.sql` file under `backend/src/prisma/migrations/` containing the actual `CREATE TABLE`/`CREATE TYPE` SQL for every Phase 1 model (User, Factory, Product, ProductSize, Color, Bundle, Location, Stock, Transaction), and (2) ran that SQL against the real Neon Postgres database, plus recorded in a `_prisma_migrations` table that this migration has been applied. That migration file is what makes the schema change reproducible — anyone else (or a future deployment) runs the same file against their own database and ends up with identical tables, instead of everyone hand-typing `CREATE TABLE` statements and hoping they match.

**Enum (in Prisma)** — a field restricted to one of a fixed set of named values, enforced by the database itself, not just application code. This schema has two: `Role` (`OWNER`/`STAFF`) and `TransactionType` (`STOCK_IN`/`STOCK_OUT`/`SAMPLE_OUT`/`SAMPLE_RETURN`). Trying to insert a `User` with `role: "MANAGER"` would fail at the database level, not just get silently accepted — a safety net beneath whatever the application code checks.

**Foreign key / relation** — e.g. `Product.factoryId` plus the `factory Factory @relation(...)` line: this tells Postgres that every `Product.factoryId` value must correspond to a real row in the `Factory` table — you can't create a `Product` pointing at a `Factory` that doesn't exist. Prisma turns each of these into a real foreign-key constraint at the database level, not just a naming convention.

**`@@unique([a, b])` (composite unique constraint)** — a uniqueness rule spanning *two* columns together, rather than one column alone. `Product` uses `@@unique([articleNo, factoryId])`: two different factories can both have an article "A101" (each unique *within* its own factory), but the same factory can't have two Products both named "A101" — enforcing "article numbers unique per Factory, never globally" (CLAUDE.md's non-negotiable rule) directly at the database level, not just in application logic.

**Routes vs. Controllers** — two files usually cooperate to handle one endpoint. The *route* file (e.g. `backend/src/routes/stock.js`) just declares "when a request hits this URL with this HTTP method, call this function" — it's a directory, not logic. The *controller* file (e.g. `backend/src/controllers/stockController.js`, once it exists) holds the actual logic that runs: reading the request, talking to the database via Prisma, deciding what to send back. Splitting them keeps "what URL triggers this" separate from "what actually happens," so a route file stays short and skimmable even as the underlying logic grows. Middleware (see above) sits in front of both — it runs before the route's handler gets control at all.

**JSON-RPC over HTTP (as used by Prisma Studio)** — a pattern where instead of many differently-shaped REST endpoints (`GET /factories`, `POST /products`, ...), a client sends every request to *one* URL (Studio uses `POST /api`) with a JSON body naming which "action" it wants (e.g. `{ action: "clientRequest", payload: { modelName: "Factory", operation: "findMany" } }`), and the server dispatches internally based on that field. Found this while tracing today's Studio investigation — Studio's browser UI talks to its own local Node server this way, which in turn calls the same generated Prisma Client this project's own code uses.

**JWT (JSON Web Token)** — a signed, tamper-proof string the server hands the client after a successful login (`authController.js`'s `login` function does this with `jwt.sign({ userId: user.id }, process.env.JWT_SECRET, { expiresIn: '7d' })`). It has three dot-separated parts: a header, a payload (here just `{ userId, iat, exp }` — deliberately *not* the role, see the decision above), and a signature computed from the first two using `JWT_SECRET`. Anyone can *read* a JWT's payload (it's just base64, not encrypted) — the security comes entirely from the signature: only someone holding `JWT_SECRET` could have produced a signature that verifies, so tampering with the payload (e.g. changing `userId`) invalidates the signature and `jwt.verify()` throws. This is what makes it "stateless" — the server doesn't need to remember anything about the token, just re-verify the signature on each request.

**Bearer token / Authorization header** — the standard way an API client attaches a credential to a request when not using cookies: an HTTP header shaped `Authorization: Bearer <token>`. "Bearer" means exactly what it sounds like — whoever *holds* (bears) the token is treated as authenticated, no further proof needed. This project's `auth.js` middleware reads this header, extracts the token after `Bearer `, and verifies it — if the header is missing or doesn't start with `Bearer `, the request is rejected before even trying to decode anything.

**Upsert** — Prisma's `upsert` means "update if a matching row exists, otherwise create it" (`UPDATE` + `INSERT` = "upsert"), based on a `where` clause that must target a unique field. `seed.js` used this originally, but has since moved to an explicit `findUnique` followed by a conditional `create`/`update` instead — `upsert`'s single `update` object can't express "only touch this one field, and only if it's currently empty," which the PIN-backfill logic needed (see the decision above). Still a useful pattern elsewhere for genuinely "create-or-replace-wholesale" cases.

**Account lockout / rate limiting a sensitive action** — deliberately slowing down or temporarily blocking further attempts after repeated failures at something security-sensitive (here, `requirePin.js`'s 5-strikes-then-15-minute-lock on the price-edit PIN). The core idea: a secret with limited entropy (a 6-digit PIN has "only" a million possibilities, versus a real password) can still be made practically unguessable if an attacker is only allowed a handful of tries before being locked out — the entropy alone isn't enough on its own, the *limit on attempts* is what actually makes brute-forcing infeasible in practice.

**Mocking `req`/`res` to test Express middleware without a server** — Express middleware is just a plain function `(req, res, next) => {...}` — nothing about it requires a real HTTP server or network round-trip. `req` and `res` can be substituted with plain JS objects that mimic just the parts the middleware actually uses (e.g. `res.status(code).json(body)` — just two chainable functions), and `next` with a function that records whether it was called. This is how `requireRole.js`/`requirePin.js` got tested here: called directly in a small script against the real seeded database, with no port to bind and nothing that could collide with a leftover process from an earlier session (see the port-collision entry in Mistakes & Fixes above).

**Username enumeration** — a security leak where an app's *error messages* accidentally reveal which usernames exist, e.g. "no such user" vs. "wrong password" as two different messages. An attacker can use that difference alone to build a list of real usernames without ever guessing a correct password, then focus password-guessing effort only on confirmed accounts. `authController.js`'s `login` deliberately returns the exact same "Invalid username or password" message and status code whether the username doesn't exist or the password is wrong, so the response itself gives nothing away.

**Prisma `select`** — controls exactly which columns a query fetches from the database, as opposed to fetching a full row and picking fields out afterward in JS. `productController.js`'s `productSelect(role)` builds this object dynamically, only including `costPrice: true` when `role === 'OWNER'` — for a STAFF request, the generated SQL query itself never asks Postgres for that column. This is different from (and stronger than) fetching everything and doing `delete product.costPrice` before responding: with `select`, there is no `costPrice` property on the resulting JS object at any point, so a later bug that spreads the object (`{ ...product }`) can't accidentally reintroduce the leak — with delete-after-fetch, it always could.

**Foreign key `RESTRICT` (referential integrity on delete)** — when table B has a foreign key pointing at table A (like `ProductSize.productId` → `Product.id`), the database needs a policy for what happens if someone tries to delete the referenced row in A while rows in B still point to it. `RESTRICT` (Prisma's default when a relation doesn't specify `onDelete`) means: refuse the delete outright, error out, change nothing. This is what blocked the test-cleanup script's `prisma.product.deleteMany()` until its child `ProductSize` rows were deleted first — a real database-level guarantee that a `Product` can't vanish out from under its own sizes.

**Prisma error codes (`P2002`, `P2003`, ...)** — when a database operation fails a constraint, Prisma Client throws an error with a specific `code` property identifying *which* kind of constraint failed, rather than a generic error. `P2002` = unique constraint violated (used in `createProduct` to detect a duplicate `articleNo`+`factoryId` and turn it into a clean 409); `P2003` = foreign key constraint violated (used there to detect a `factoryId` that doesn't correspond to a real `Factory` and turn it into a 404). Catching these by code, right where the operation that could trigger them runs, avoids a separate "check first" query that could race against another request doing the same thing at the same moment.

**Middleware chaining / short-circuiting** — an Express route can list more than one middleware function before its final handler (e.g. `router.patch('/:id', requireAuth, requireRole('OWNER'), requirePinForPriceEdits, updateProduct)`); each one runs in order and must call `next()` to let the next one run. If any middleware in the chain sends a response instead of calling `next()` (as `requireRole`/`requirePin` do on failure, via `sendError`), everything after it — including the real route handler — never runs at all. This is what structurally guarantees `04_API_SPEC.md`'s "do not partially apply the update" requirement for `PATCH /api/products/:id`: if the PIN check fails, `updateProduct` is never even called, so there's no code path where a partial write could happen.

**Case-sensitive vs. case-insensitive matching (Postgres/Prisma)** — a plain Postgres `UNIQUE` index (what `name String @unique` in the schema creates) compares text byte-for-byte, so `"Navy"` and `"navy"` are two different values as far as the database is concerned — the constraint only blocks an exact repeat. Prisma exposes case-insensitive comparison via `mode: 'insensitive'` on a string filter (`colorController.js`'s `findFirst({ where: { name: { equals: trimmed, mode: 'insensitive' } } })`), which Prisma translates into a case-folding SQL comparison instead of a plain `=`. This is an application-level check, separate from the database's own constraint — the two aren't the same guarantee, which is why both the pre-check *and* a `P2002` catch exist side by side (see the decision above).

**Race condition / lost-update problem** — happens when two things read the same piece of shared state, both decide what to do based on that read, and both then write — without either one seeing what the other did. Concretely here: two `STOCK_OUT` requests against the same Stock row could both read `qtySets: 5`, both compute "5 - 3 = 2, that's fine," and both write `2` — even though the *correct* answer after two separate `-3` operations should have been `-1` and rejected. The fix isn't "check more carefully in JavaScript" (any read-then-write-later pattern has this same gap, no matter how careful the check) — it's making the check and the write a single, indivisible database operation, which is what `POST /api/transactions`'s WHERE-clause guard does (see the decision above).

**Prisma interactive transactions (`$transaction(async (tx) => {...})`)** — wraps a whole sequence of Prisma calls in one real Postgres transaction (`BEGIN` ... `COMMIT`/`ROLLBACK`), using the special `tx` client passed into the callback instead of the normal `prisma` client. If the callback throws (for any reason — a thrown validation error, a database error, anything), Prisma automatically rolls back every write the callback made, even ones from earlier in the same callback that individually "succeeded" before the throw. This is different from Prisma's other transaction form, the array form (`$transaction([op1, op2])`), which only runs a fixed, pre-decided list of operations together — it can't express "read a value, then decide based on it whether to error out," which `createTransaction` in `transactionController.js` needs to do (find-or-create the Stock row, conditionally reject, only then insert the Transaction record).
Worked example, traced through concretely: if `tx.stock.upsert` and `tx.stock.updateMany` both already ran successfully — the Stock row's new quantities are written, but only as an uncommitted version tagged to this transaction (Postgres's MVCC means no other connection can see it yet, though this same transaction can read its own writes) — and then `tx.transaction.create` throws for any reason, Prisma issues `ROLLBACK`. That discards *everything* since `BEGIN` as one unit: the quantity change reverts, and if `upsert` had just created a brand-new zero-value Stock row (first-ever activity for that bundle/location), that row is gone entirely, not merely reset. The database ends up exactly as if the request had never arrived — there's no partial-commit state to reason about, because Postgres transactions don't have one.

**Express error-handling middleware (the 4-argument signature)** — a normal Express middleware function takes 3 arguments, `(req, res, next)`. An error handler takes 4: `(err, req, res, next)` (`errorHandler.js`). Express doesn't detect this by name or by where it's defined — purely by counting the function's parameters. Write one with only 3 params and Express treats it as ordinary middleware that happens to never get called, since nothing ever routes a normal request to it; the `next` parameter has to stay even though `errorHandler.js` never calls it, just to keep the arity at 4. It also has to be registered with `app.use()` *after* every route it's meant to protect — Express walks the middleware stack in registration order, and only forwards an error to handlers registered later than wherever it was thrown.

**Sync throw vs. async rejection in Express route handlers** — a route handler that directly does `throw new Error(...)` has always been safely caught by Express, in every version — that's a normal synchronous exception, and Express's own request-dispatch code is wrapped in a try/catch that turns it into a call to the error-handling middleware. An `async` handler that throws is different under the hood: since the function returns a Promise, throwing inside it produces a *rejected Promise*, not an exception the calling code's try/catch can see directly. Express 5 (used in this project) auto-detects when a route handler returns a Promise and attaches a `.catch()` that forwards any rejection into the same error-handling pipeline — this project's actual error scenarios (like `transactionController.js`'s `await tx.transaction.create(...)` failing) are exactly this async case, not the sync one. This wasn't automatic in Express 4 — an unhandled rejection there would have just hung the request or crashed the process, which is one reason this project is on Express 5 rather than 4.
